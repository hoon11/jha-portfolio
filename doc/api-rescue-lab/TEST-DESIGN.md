# API Rescue Lab 테스트 설계

요청이 느리거나 응답 형식이 잘못돼도 사용자가 현재 상태를 이해하고 다시 조회할 수 있어야 한다. [ADR-0003](../adr/0003-keep-api-rescue-lab-browser-local-and-deterministic.md)에 따라 브라우저 안의 시뮬레이터로 실패를 재현한다.

| 위험 | 입력·조작 | 기대 결과 | 자동 테스트 |
| --- | --- | --- | --- |
| 느린 요청 때문에 화면이 계속 대기하거나 취소한 응답이 복구 결과를 덮어쓴다. | 느린 시나리오에서 가상 시간을 1,999ms까지 진행한 뒤 1ms를 더 진행한다. 같은 시나리오를 재시도하고 정상 조회로 바꾼다. | 1,999ms에는 로딩 상태다. 2,000ms에 타임아웃을 표시하고 타이머를 정리한다. 재시도는 동일하게 실패한다. 정상 조회로 복구한 뒤에도 성공 상태를 유지한다. | [컴포넌트의 타임아웃과 복구](../../components/api-rescue-lab.test.tsx#L86) |
| 잘못된 응답이 이전 결과를 지우거나 정상 데이터처럼 표시된다. | 정상 조회 뒤 잘못된 응답을 실행한다. 초기 화면에서도 잘못된 응답과 재시도를 실행한다. 검증 함수에는 잘못된 타입이나 중복 ID를 전달한다. | 마지막 성공 데이터가 있으면 이전 결과로 표시한다. 성공한 조회가 없으면 빈 화면 상태를 유지한다. 검증 함수는 잘못된 입력을 거부한다. | [컴포넌트의 이전 데이터와 초기 실패](../../components/api-rescue-lab.test.tsx#L51), [응답 검증 함수](../../lib/rescue-lab.test.ts#L17) |
| 이전 요청의 완료가 최신 요청의 상태를 덮어쓴다. | 요청 1과 요청 2를 차례로 시작한 뒤, 요청 2의 완료 전후로 요청 1의 완료 액션을 전달한다. | 현재 요청 ID와 다른 완료 액션은 상태를 바꾸지 않는다. 마지막 성공 데이터가 유지된다. | [리듀서의 완료 순서](../../lib/rescue-lab.test.ts#L4) |

컴포넌트 테스트는 실제 시뮬레이터와 가상 타이머로 상태 메시지, 남은 타이머, 데이터 표시를 확인한다. 화면은 로딩 중 두 번째 요청을 막으므로 완료 순서는 리듀서에 액션을 직접 전달해 확인한다.

[브라우저 확인 절차](../PRODUCTION_CHECKLIST.md#4-api-rescue-lab-verification)는 실제 화면에서 정상 조회, 실패 후 이전 결과 표시, 타임아웃과 복구를 확인하는 절차다. 이 문서는 테스트 설계를 설명한다. 배포 실행 결과는 검증한 커밋과 함께 기록한다.
